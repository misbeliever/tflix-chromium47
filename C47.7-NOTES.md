# C47.7: old-browser provider install preflight

## Evidence

During the live C47.6 check, the TV at 192.168.50.39:47994 answered GET /health with HTTP 200 and {"ok":true}, both without Origin and with the TizenBrew app Origin http://127.0.0.1:8081. This confirms a listening relay, not successful provider installation.

A read-only OPTIONS request to /packs/install with Access-Control-Request-Method: POST and Access-Control-Request-Headers: content-type returned 204 but Access-Control-Allow-Headers: *. Chromium 47 cannot use that wildcard to authorize the JSON Content-Type header. MDN’s browser compatibility data places wildcard support at Chrome 63: https://github.com/mdn/browser-compat-data/blob/main/http/headers/Access-Control-Allow-Headers.json . The app’s catch-all network error misleadingly calls this blocked request an unreachable relay.

## Fix and checks

The shared relay response now explicitly allows Content-Type and Range. No origins, methods, loopback write restrictions or pairing requirements are broadened. The corrected Node 4 launcher-style test first failed on the published C47.6 service with the new explicit-header assertion. It then passes on this build, checking the real OPTIONS response before the existing synthetic provider install/load/resolve/uninstall and HLS checks. Production build/ES5 checks and exit checks also pass.

The preflight assertion checks the protocol required by Chromium 47; it does not run the actual TV browser. Live TV installation and external provider/TLS/playback have not been tested. Newer provider scripts can still be incompatible with Node 4.
